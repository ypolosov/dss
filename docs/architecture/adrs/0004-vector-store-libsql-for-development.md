# ADR-0004: Vector Store — LibSQLVector for Development, PgVector for Production

## Status

Accepted (amends ADR-0003 Vector Store Client decision)

## Date

2026-03-15

## Context and Problem Statement

ADR-0003 specifies PgVector as the vector store client, and the C4 model defines `vectorDb` as "PostgreSQL + pgvector". However, requiring a running PostgreSQL instance with the pgvector extension for local development creates unnecessary friction. The implementation uses `@mastra/libsql` (LibSQLVector) instead, which provides zero-infrastructure local development via a file-based SQLite database. The Mastra framework offers a uniform `MastraVector` interface across all vector store backends, making the swap trivial.

## Decision Drivers

- CONS-002: NestJS + Mastra tech stack (constraint)
- QA-001: RAG query response <= 10 sec including LLM call (H,M)
- CONC-005: Developer experience — no PostgreSQL required for local dev
- Zero-config local development (`file:../../vectors.db`)

## Considered Options

1. LibSQLVector for development, PgVector for production
2. PgVector only (original ADR-0003 approach)
3. In-memory vector store for development

## Decision Outcome

Chosen option: "LibSQLVector for development, PgVector for production", because it eliminates the PostgreSQL dependency for local development while preserving the production-grade vector store path via the identical `MastraVector` interface.

### Implementation

The vector store factory (`src/mastra/vector/index.ts`) selects the backend via the `VECTOR_STORE_TYPE` environment variable:

| Environment | `VECTOR_STORE_TYPE` | `VECTOR_DB_URL` | Backend |
|-------------|---------------------|-----------------|---------|
| Development | `libsql` (default) | `file:../../vectors.db` | `@mastra/libsql` LibSQLVector |
| Production | `pg` | PostgreSQL connection string | `@mastra/pg` PgVector |

The `MastraVector` interface is identical across backends — switching requires only changing the env var and installing `@mastra/pg`.

### Impact on ADR-0003

ADR-0003 defines the Vector Store Client component as "pgvector operations (upsert, query, delete)" using `PgVector`. This ADR amends that decision:

- The component responsibility remains unchanged: upsert, query, delete operations
- The Mastra primitive changes from `PgVector` only to `LibSQLVector | PgVector` depending on environment
- The performance budget (QA-001) is unaffected — LibSQLVector is faster for local development due to no network overhead

### Consequences

#### Good

- Zero-config local development — `npm run dev` works without PostgreSQL or Docker
- File-based vector DB (`vectors.db`) is portable and committed to `.gitignore`
- Identical `MastraVector` interface — no code changes between environments
- Production path to PgVector remains open via one config change + `@mastra/pg` install
- Faster developer onboarding — no infrastructure prerequisites

#### Bad

- LibSQLVector and PgVector may have subtle behavioral differences (distance metrics, HNSW tuning)
- Two vector backends to test and maintain awareness of
- LibSQLVector is not suitable for production at scale (no HNSW index, no concurrent writes)

#### Neutral

- The `vectors.db` file is ephemeral — can be regenerated by re-running ingestion
- Embedding dimensions and index names are consistent across both backends

## Pros and Cons of the Options

### Option 1: LibSQLVector for development, PgVector for production

- Good, because zero-infrastructure local development
- Good, because `MastraVector` interface is identical — no code branching
- Good, because aligns with CONS-002 (Mastra tech stack — both are Mastra primitives)
- Bad, because two backends to be aware of (potential subtle differences)

### Option 2: PgVector only (original ADR-0003 approach)

- Good, because single backend — no environment differences
- Good, because production-grade from day one
- Bad, because requires PostgreSQL + pgvector extension running locally
- Bad, because Docker Compose or local PostgreSQL install adds onboarding friction (CONC-005)
- Bad, because slows down rapid iteration in early development phase

### Option 3: In-memory vector store for development

- Good, because fastest possible local performance
- Bad, because data lost on every restart — must re-ingest constantly
- Bad, because no Mastra-native in-memory vector store — would require custom implementation
- Bad, because violates CONS-002 (not a Mastra primitive)
